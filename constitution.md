# Project Constitution: Sales Dashboard for Customers

## 1. Purpose

Provide customers with a mobile-first dashboard that lets them read their
sales data in a clear, fast, and simple way. The system ingests raw sales
data from an existing source database, transforms it into optimized models
for fast response, and serves it through a FastAPI backend to a React
mobile-first frontend.

## 2. Fundamental Principles

### 2.1. Mobile-First, Always
- Every UI decision starts from the mobile viewport. Desktop is a progressive
  enhancement, never the design target.
- Tailwind CSS is the styling system. No custom CSS frameworks.
- Touch targets, typography, and spacing are tuned for phone screens first.
- Charts and tables must remain readable at 375px width.

### 2.2. Backend as ETL, Not Just API
- The FastAPI backend does **not** query the origin database on every request.
- The origin data is transformed by a **dedicated worker** into optimized
  models stored in PostgreSQL.
- The API serves pre-computed, denormalized data tuned for fast response.
- "Fast response" means the API answers in under 200ms for typical queries
  on the optimized models.

### 2.3. Source of Truth Is External
- The **origin database already exists** and is owned by another system.
  The dashboard does not modify it, migrate it, or assume ownership of it.
- The dashboard owns its **own PostgreSQL schema** with transformed models.
- Custom queries against the origin are isolated in a dedicated module.

### 2.4. Separated Concerns by Folder
- `backend/` — FastAPI application, models, ETL orchestration, API routes.
- `integration/` — Worker process that reads origin data and writes to the
  optimized models. Runs on its own schedule.
- `frontend/` — React mobile-first application.
- `custom_queries/` — Versioned SQL queries against the origin database.
  Isolated so schema changes in the origin are easy to track.

### 2.5. Fixed Technology Stack
- **Backend:** Python 3.11+, FastAPI, Uvicorn, SQLAlchemy, Alembic
- **Database:** PostgreSQL (dashboard-owned schema)
- **Worker:** Python 3.11+, APScheduler or Celery (TBD in plan phase)
- **Frontend:** React 19, Vite, Tailwind CSS, Recharts, Lucide React,
  html2canvas, ReportLab (backend-side PDF generation)
- **Container:** Docker Compose (backend, worker, frontend, postgres)
- **Auth:** To be defined in plan phase (deferred)

### 2.6. Data Tuning Over Raw Storage
- The origin data is assumed to be in a shape that is not optimal for
  mobile reads (many joins, wide rows, slow aggregates).
- The worker pre-aggregates by day, week, month, and per-product as needed.
- Materialized views or summary tables are the preferred tuning mechanism.
- If the origin already provides aggregates, the worker still reshapes them
  into the dashboard's own models.

## 3. Constraints

- The origin database credentials are read-only. Never write to it.
- The dashboard schema is versioned with Alembic. No unversioned migrations.
- The worker must be idempotent: re-running it does not duplicate data.
- The worker must be safe to restart at any time without corrupting state.
- The frontend never calls the origin database directly, only the FastAPI API.
- All API responses must be JSON. No HTML rendering from the API.
- PDF exports (ReportLab) are generated by the backend, not the frontend.
- html2canvas is used only for client-side chart snapshots, never as the
  primary PDF path.
- Mobile-first means the first pixel rendered is the phone layout.

## 4. Success Criteria

- A customer can open the dashboard on a phone and see their sales summary
  within 2 seconds on a 4G connection.
- The API returns typical queries in under 200ms on the optimized models.
- The worker completes a full refresh of the optimized models in a bounded
  time window (target: under 5 minutes for the initial scope).
- A customer can export a PDF summary of their sales from the mobile UI.
- The project layout is clean enough that a new developer can find the
  origin query, the transformation logic, and the API route in under
  one minute each.
