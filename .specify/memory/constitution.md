# Sales Dashboard for Customers Constitution

Provide customers with a mobile-first dashboard that lets them read their sales data in a clear,
fast, and simple way. The system ingests raw sales data from an existing source database,
transforms it into optimized models for fast response, and serves it through a FastAPI backend to
a React mobile-first frontend.

## Core Principles

### I. Mobile-First, Always

- Every UI decision MUST start from the mobile viewport. Desktop is a progressive enhancement,
  never the design target.
- Tailwind CSS MUST be the styling system. No custom CSS frameworks.
- Touch targets, typography, and spacing MUST be tuned for phone screens first.
- Charts and tables MUST remain readable at 375px width.

Rationale: customers read their sales on phones; a layout designed for desktop and shrunk later
fails exactly where the product is used.

### II. Backend as ETL, Direct Reads by Exception

- By default the FastAPI backend MUST NOT query the origin database on every request: origin data
  MUST be transformed by a dedicated worker into optimized models stored in PostgreSQL, and the
  API MUST serve pre-computed, denormalized data tuned for fast response.
- Exception — direct reports: a report spec MAY declare direct mode when its data is already
  shaped and maintained by another process (an existing, tested BI table or a reporting schema of
  a PostgreSQL source). Direct reads MUST use only engine-generated aggregate SQL over the tables
  and columns the spec declares, in a read-only session with a statement timeout, a row cap and a
  result cache; the source MUST be explicitly enabled for direct reads by the super user; product
  tables MUST never be readable this way.
- "Fast response" means the API answers typical queries on the optimized models in under 200ms;
  direct reports answer from cache in under 200ms and cold within the declared timeout.

Rationale: the origin schema is usually not shaped for mobile reads, so heavy work is done ahead of
time; when another process already did that work, copying it again adds delay and failure points
without value.

### III. Source of Truth Is External

- The origin database already exists and is owned by another system. The dashboard MUST NOT
  modify it, migrate it, or assume ownership of it.
- The dashboard owns its own PostgreSQL schema with transformed models.
- Custom queries against the origin MUST be isolated in a dedicated module.
- Origin connections MUST be defined in the product's data-source catalogue (PostgreSQL, SOAP,
  REST in this version), managed by the super user, with credentials encrypted — never in a
  connection-string setting.

Rationale: another system depends on the origin database; the dashboard is a read-only consumer
and must not put it at risk.

### IV. Separated Concerns by Folder

- `backend/` — FastAPI application, models, ETL orchestration, API routes.
- `integration/` — Worker process that reads origin data and writes to the optimized models.
  Runs on its own schedule.
- `frontend/` — React mobile-first application.
- `custom_queries/` — Versioned SQL queries against the origin database, isolated so schema
  changes in the origin are easy to track.
- `deploy/` — Edge proxy (Caddy) configuration and image, compose overrides, per-deployment
  branding assets. No application logic.
- Customer projects (one folder per project with its numbered Spec Kit specs and artifacts) live
  in the installation's `projects/` folder, never in this repository.
- `cli/` — `bizview-cli` (workspace init, validation, describe) and the artifact schemas shared
  with the backend.
- `cli/bizview_cli/workspace_template/` — the Spec Kit preset, extension, and agent rules for
  customer workspaces (package data of the CLI). Customer workspaces themselves live in the
  customer's private repository, never here.

PDF report code belongs to the backend (`backend/app/reports/`), since reports are rendered from
the same services as the JSON API.

Code MUST live in the folder that owns its concern; cross-folder shortcuts (for example, origin
SQL embedded in `backend/`) are not allowed.

Rationale: a new developer must be able to find the origin query, the transformation, and the
API route quickly (see Success Criteria).

### V. Fixed Technology Stack

- **Backend:** Python 3.11+, FastAPI, Uvicorn, SQLAlchemy, Alembic, ReportLab (PDF generation).
- **Database:** PostgreSQL (dashboard-owned schema).
- **Worker:** Python 3.11+, APScheduler (single scheduler process; no message broker).
  PostgreSQL sources stream the validated query result with COPY (text format) from a read-only
  session straight into typed staging tables; REST/SOAP records are batched with Polars into the
  same staging COPY; an optional declarative transform stage runs in Polars (Rust engine) between
  extraction and load; report aggregation and rollups stay in PostgreSQL SQL.
- **Frontend:** React 19, Vite, Tailwind CSS, Recharts, Lucide React, html2canvas; the built app
  is served by **Caddy**, the single edge, which also proxies `/api` to the backend (single
  origin) and provides automatic HTTPS.
- **Container:** Docker Compose (caddy, backend, worker). PostgreSQL is always external: the BI
  database for the product and a separate external test database for the suites; no database
  container.
- **Auth:** email + password, Argon2id password hashes, server-side sessions stored in
  PostgreSQL and carried by an HttpOnly cookie. An installation MAY also enable sign-in with
  Google as an **additional** identity for users who already exist (feature 027): it is off by
  default, configured per installation with that installation's own OAuth client, invite-only
  (it never creates or promotes a user), opt-in per attempt by the person signing in, and it never
  substitutes for the second factor that the `internet` profile requires of administrators.
  Password sign-in MUST remain available whenever it is today, so an installation can never be
  locked out through its identity provider.

- **AI:** optional provider layer in the backend — Claude through the official `anthropic` SDK
  (default), or any OpenAI-compatible endpoint (including local models) over `httpx`.
- **Security & sources:** `cryptography` (AES-256-GCM for secrets at rest), `pyotp` + `segno`
  (two-step sign-in), origin connectors `psycopg` (PostgreSQL), `zeep` (SOAP), `httpx` (REST).
- **Vibe reporting:** GitHub Spec Kit (presets + extensions) for authoring; `sqlglot`
  (read-only SQL enforcement), `jsonschema` (artifact validation).
- **Distribution:** versioned multi-arch images on GitHub Container Registry; checks and releases
  on GitHub Actions; customers install with `deploy/install.sh`.

Adding, replacing, or removing a stack component MUST go through a constitution amendment.
Supporting libraries (routing, hashing, drivers, test and dev tools) are not stack components;
each MUST be listed with its reason in the feature plan.

Rationale: a fixed stack keeps the project small and predictable for every contributor.

### VI. Data Tuning Over Raw Storage

- The origin data is assumed to be in a shape that is not optimal for mobile reads (many joins,
  wide rows, slow aggregates).
- The worker MUST pre-aggregate by day, week, month, and per-product as needed.
- Materialized views or summary tables are the preferred tuning mechanism.
- If the origin already provides aggregates, the worker MUST still reshape them into the
  dashboard's own models.

Rationale: the dashboard's models are the contract with the API; depending on the origin's shape
would couple the two systems.

### VII. One Product, Many Installations

- The repository MUST contain only the generic product: no customer names, logos, addresses, or
  credentials.
- Every customer difference MUST be configuration (installation settings, branding folder,
  source-query profile) — never a code fork or a per-customer code folder.
- Installations MUST run published, versioned images and upgrade by changing the version.

Rationale: one codebase serves every customer and every customer receives every fix.

### VIII. AI Is Optional and Private

- AI MUST be off by default and the product MUST work fully without it.
- Only aggregates and metadata composed by product code may be sent to an AI provider — never raw
  source records, credentials, or users' personal data. Each AI feature MUST document its inputs.
- Provider keys MUST never be returned by the API, shown in the interface, or logged.
- Customers MUST be able to choose a local model so no data leaves their infrastructure.

Rationale: customers trust the product with their business data; AI must add value without
becoming a data leak or a hard dependency.

### IX. Spec-Driven Reporting ("Vibe Reporting")

- Every integration (ETL) and every report MUST be defined by an approved, complete GitHub Spec Kit
  spec in the customer's workspace; one integration spec may serve many report specs.
- The engine MUST refuse to load, run, or show anything whose spec is missing, incomplete, or
  changed after validation. AI is used only where an approved report spec declares it, with the
  aggregates that spec lists. There is no free-form AI entry point in the product.
- Customer logic is declarative (YAML + read-only SQL / request definitions); no customer code in
  the product.
- Work is organised in projects: each project is a folder with its own numbered specs (001, 002,
  …) covering sources, integrations, reports and distribution. The in-app agent changes a project
  only through Spec Kit commands (constitution, specify, clarify, plan, tasks, analyze, checklist,
  implement, converge) and answers only about BizView, reports, integrations, ETL and sources.

Rationale: specs make every number explainable and reviewable, keep AI work bounded, and let
customers build reports themselves — "vibe reporting".

## Constraints

- Origin database credentials are read-only. The dashboard MUST NEVER write to the origin.
- Credentials of any kind (origin passwords, tokens, keys, two-step secrets) MUST be encrypted at
  rest with a key held outside the database, and MUST be write-only: never returned, shown, or
  logged.
- Every installation MUST declare its security profile (`SECURITY_PROFILE`). `private` allows
  plain HTTP for the product and its sources; `internet` requires HTTPS/TLS for the product and
  every source connection, two-step sign-in for administrators, sign-in throttling, and step-up
  confirmation. Installations reachable from the internet MUST run `internet`.
- The product schema MUST be versioned with Alembic. Integration dataset schemas
  (`ds_<integration>`) are created and altered only by the engine from validated contracts.
- The worker MUST be idempotent: re-running it does not duplicate data.
- The worker MUST be safe to restart at any time without corrupting state.
- The frontend MUST NOT call the origin database directly, only the FastAPI API.
- All API responses MUST be JSON, except PDF export downloads (`application/pdf`). No HTML
  rendering from the API.
- PDF exports MUST be generated by the backend with ReportLab, not by the frontend.
- html2canvas MUST be used only for client-side chart snapshots, never as the primary PDF path.
- Mobile-first means the first pixel rendered is the phone layout.
- Every user-visible text (screens, server messages, PDFs, emails, agent replies) MUST exist in
  Spanish and English; authored workspace content is shown as written.

## Success Criteria & Quality Gates

A feature is not complete unless it keeps these targets met:

- A customer can open the dashboard on a phone and see their sales summary within 2 seconds on a
  4G connection.
- The API returns typical queries in under 200ms on the optimized models.
- The worker completes a full refresh of the optimized models in a bounded time window (target:
  under 5 minutes for the initial scope).
- A customer can export a PDF summary of their sales from the mobile UI.
- A new developer can find the origin query, the transformation logic, and the API route in
  under one minute each.

- This constitution supersedes other project practices. Specs, plans, and tasks MUST be checked
  against it (the plan template's Constitution Check gate).
- Amendments are made by editing this file through `/speckit-constitution`, with a Sync Impact
  Report describing what changed and why.
- Versioning follows semantic versioning:
  - MAJOR: a principle or constraint is removed or redefined incompatibly.
  - MINOR: a principle or section is added or materially expanded.
  - PATCH: clarifications and wording fixes with no change in meaning.
- Any deviation from a principle MUST be justified in the plan's Complexity Tracking section, or
  the constitution amended first.
- Reviews MUST verify compliance with the Constraints and Quality Gates above.
